## 0. 先界定「上线」是什么意思

这个项目**不是一个接流量的服务**：没有常驻进程、没有数据库、没有用户账号。
它的交付形态是「**别人 clone 下来自己跑**」，所以「上线」= 发布出去给人用。
据此，真正的风险是这五条，本文所有测试都围着它们转：

| # | 风险 | 为什么它比「吞吐/高可用」重要 |
| --- | --- | --- |
| 1 | **密钥泄漏** | 一次就够。仓库是公开的，泄漏不可撤回 |
| 2 | **别人跑不起来** | 交付物就是「照着 README 能跑通」，跑不通等于没交付 |
| 3 | **花钱失控** | 它会真的调模型、真的花钱；失控的是用户的钱 |
| 4 | **数字是假的** | 项目的价值就是那几个数字，假一个就全废 |
| 5 | **坏的时候不体面** | 陌生人第一次失败往往就是坏 key / 断网，那时最需要说人话 |

**不测的**：压测、并发、高可用、灾备 —— 没有常驻服务，测这些是走过场。

## 3. 发现的问题（按严重度）

### P0 — 阻断发布

#### P0-1 README 的「这是什么 / 快速开始 / 架构」是占位

- **现象**：`README.md` 里三处写着「（占位）」，而快速开始是陌生人唯一的入口。
- **为什么是 P0**：本项目的交付标准是「**陌生人 5 分钟内跑出结果**」（需求 G4）。
  一个快速开始是占位的仓库，等于没有交付 —— 哪怕代码全绿。
- **状态**：✅ **已修**（`f53fce2`）。补了「这是什么 / 快速开始（含实测耗时成本）/
  架构图 / 已知限制」四节，并且**照着自己写的命令在全新环境里逐条跑过**。
  顺带记录实测依赖版本组合（PRE-6）与镜像 403 的回退命令（PRE-8）。

### P1 — 修掉才敢上线
#### P1-1 provider 挂死 → 调用无限等（有界性）

- **现象**：自建「收了请求不回应」的假服务，客户端 **20 秒未返回**。
- **影响**：litellm 默认超时 600 秒 × `max_steps=20` = **最长约 3 小时**。
  用户以为程序卡死，只能 Ctrl+C。
- **状态**：✅ **已修**（`ff0e821`）。`LiteLLMClient` 显式传 `timeout`，
  新增 `FIVEWHYS_LLM_TIMEOUT_S`（默认 60 秒）；测试用挂死服务验证「必须在我们给的
  超时内返回」。

#### P1-2 清理陈旧场景包会「删一半就崩」

- **现象**：陈旧场景包里有一个子目录时，原实现（逐个 `unlink()` 再 `rmdir()`）
  抛 `PermissionError`，**留下删了一半的目录**（实测：`scenario.json` 还在、`logs.jsonl` 已没）。
- **附带**：只判断「有没有 `scenario.json`」就删，太宽（别的工具也用这个文件名）；
  且 `is_symlink()` 对 Windows **junction 返回 False**，而 junction 不需要管理员权限。
- **状态**：✅ **已修**（`cdfb69d`）。整目录 `rmtree` + 必须是「目录名 == 自己
  `scenario_id`」的真场景包 + 符号链接/junction 都拦 + 拒绝清理盘根/家目录/源码目录，
  且安全检查跑在**写文件之前**（这个顺序问题写测试时才想清楚）。

#### P1-3 坏 key → 结果表格前甩 60 行 traceback，且不说原因

- **现象**：坏 key 时输出 ~80 行，含 litellm 内部 traceback 和
  「Give Feedback / Get Help」横幅；表格备注只写「未提交结论（error）」。
- **根因**：全项目**没有一处配置日志**；主循环用 `logger.exception`；
  litellm 的横幅走 `print`（压日志级别无效）。
- **状态**：✅ **已修**（`ff0e821`）。`fivewhys/logs.py` 统一收口（默认 WARNING 一行、
  无堆栈；`-v` 出 DEBUG+堆栈），`suppress_debug_info` 压掉横幅，
  demo 按错误类型给出可执行提示。**实测输出 80 行 → 18 行**。

#### P1-4 上下文预算存在越界（NFR-11）

- **现象**：用最宽参数问 `query_logs`，整段返回 **6108 字符** > 6000 的线。
- **根因**：预算只卡**明细行**，表头（摘要 + 元信息 + 截断提示）加在预算之外。
- **更值得记的**：当时的测试写成 `<= MAX + 200`，那个容差正好掩盖了越界 ——
  **带容差的断言等于没有断言**。
- **状态**：✅ **已修**（`2098c5b`）。拼装与裁剪收敛到一个入口 `render_block()`，
  表头和截断提示先扣额度；测试去掉容差。实测最大 6108 → **5950**。

#### P1-5 密钥忽略规则太窄

- **现象**：`.gitignore` 只忽略 `.env` / `.env.local`，
  **`.env.production`、`.env.bak` 都不忽略** —— 一次 `git add -A` 就可能提交带密钥的变体。
- **状态**：✅ **已修**（`7e3e762`）。`.env*` 全忽略，只保留 `.env.example`；
  顺带补 `*.pem` / `secrets.*` / `credentials.*`。

#### P1-6 依赖约束写错了下界

- **现象**：声明 `litellm>=1.0`，但我们用到的 `suppress_debug_info`、
  `_hidden_params["response_cost"]`、`acompletion(timeout=...)` 都不是 1.0 就有的。
- **影响**：声称支持一个从没跑过的版本 = 把问题留给第一个装它的人。
- **状态**：✅ **已修**（`59e4cb9`）。下界 = 实测版本（`litellm>=1.101`），上界 = 下一主版本；
  README 记录实测版本组合，并说明全新安装可能拿到 `1.102.0`。

#### P1-7 全量评测没有总预算闸门

- **现状**：单次有 $0.10 硬上限（已实测有效），但 `--runs 100` 这种**多轮**调用
  原先没有任何全局保险丝。NFR-2 要求全量 ≤ $5。
- **状态**：🟡 **已修一半**。`demo_m1.py` 加了 `--max-total-usd`（默认 $0.50）：
  超了就停在原地、打印已花多少、并**拒绝给出验收结论**（没跑满不判定通过，
  判定逻辑抽成纯函数 `judge()` 单独测）。
  **M6 的评测执行器仍需要一个自己的总预算** —— 那是真正会跑 100 次的地方，
  归 FIV-20。

#### P1-8 已发布的准确率数字**样本不足**，且观察到了失败

- **现象**：M1 验收第一版是「100%（5/5）」。之后又跑了几批做加固验证，
  其中**一批 2 次里有 1 次没到 80 分**（累计 14/15 ≈ 93%）。
  那次的轨迹没留下来，所以**至今不知道它错在哪**。
- **为什么算 P1**：这个数字是项目对外的主要交付物。
  「一个 5 次批次」不足以下「准确率 100%」这种结论 —— 那是估计值，不是常量。
  严格说，**当时写进 README 的那行数字是过度自信的**。
- **状态**：✅ **数字已改正**（README 改为累计口径 93%（14/15），并写明样本构成）。
  ⬜ **根因未查明** —— 需要 trace 落盘（FIV-19）才能事后审计单个失败样本。
  这是给 FIV-19 的一个具体动机，不再是「M5 该做的事」这种空话。

#### P1-9 输出侧没有闸门（无 `max_tokens`；巨型响应直接进上下文）

- **现象（实测）**：
  1. 我们的请求里**没有 `max_tokens`**（发出去的字段只有 `messages` / `model` /
     `temperature`）—— 输出长度完全由 provider 决定。
  2. 一个 **8MB 的回复被原样带进上下文**（客户端照单全收 8,000,000 字符），
     **单次调用记账 $0.84** —— 是单次硬上限（$0.10）的 **8 倍**，
     而成本闸门是在调用**之后**才检查的，拦不住这一刀。
     更糟的是它会进对话历史，下一次请求整个再发回去 —— 成本**平方级**增长。
- **状态**：✅ **已修**。新增 `FIVEWHYS_MAX_OUTPUT_TOKENS`（默认 2000）随请求发出；
  再加一道**响应侧**兜底：单次回复 > 10 万字符直接报错（`OversizedResponseError`），
  由主循环记成一次 `error`（需求 §6.2：不计入准确率分母）。
  兜两道是有意的 —— `max_tokens` 是**请求**，provider 可以不理它
  （自建端点 / 代理 / 兼容层都可能）；响应侧才是硬边界。
  宁可报错也不截断：截断会把一份垃圾留在历史里，之后每次调用都带着它。
- **顺带修正一个认知**：单次硬上限（$0.10）**不是严格上界** ——
  它在调用**之后**才检查，所以最坏情况可以超一次调用的量。
  加上 `max_tokens` 之后，单次调用的输出成本上界才真正可控。
