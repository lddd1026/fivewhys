## 三条拆解原则

1. **先竖切，再横扩** —— M1 就做「一个服务 + 一种故障 + 一个工具」的完整链路，
   哪怕很糙。**先证明路走得通，再变复杂。**
2. **尽早拿到第一个数字** —— M6 必须产出真实评测数据。如果项目不行，
   你在第 3 周就发现了，而不是第 4 周。
3. **每个目标结束都有能跑的东西** —— 不允许出现「写了三天但什么都跑不了」的阶段。

## 🟡 M1 · 最细竖切 · 3 天 【当前目标】

**🎯 解锁**：**agent 第一次自己查出根因**（哪怕准确率只有 50%）

这是整个项目**心理上最关键的一步**。前面都在造布景，这个目标结束时演员才第一次上场。

**覆盖需求**：FR-1（1 个服务）、FR-2（1 种故障）、FR-3、FR-4、FR-5（`query_logs`）、
FR-6、FR-15（简化版场景包）

| 任务 | 内容 | 状态 |
| ---- | ---- | ---- |
| FIV-1 | 实现 `db_pool_exhausted` 故障注入 | ✅ |
| FIV-2 | 实现 `query_logs` 工具（含 NFR-11 上下文预算） | ✅ |
| FIV-3 | 把工具注册进 registry 并写单测 | ✅ |
| FIV-4 | 实现 agent 主循环 | ✅ |
| FIV-5 | 端到端手工验证 | ✅ |

**交付物**：一条能跑出诊断结论的命令

**验收**：跑 5 次，**至少 3 次给出正确根因**

> **✅ 2026-09-10 验收通过：5 次全部 100%。**
>
> | 模型 | 准确率 | 平均调用 | 平均成本 | 平均耗时 |
> | ---- | ------ | -------- | -------- | -------- |
> | `deepseek/deepseek-chat` | 100%（5/5） | 8.0 | $0.0031 | 13.8s |
>
> 它的推理路径（`--trace` 实测）：指标拿到异常时间点 → 拓扑确认下游是谁 →
> 日志看症状 → 查下游指标**排除**它们 → **配置里找到 `db.pool_size: 50 -> 5`** →
> 发布记录排除嫌疑 → 提交。**它是自己走到配置那一步的**，这正是这个场景要考的。
>
> ⚠️ 这一步故意做糙：不美化、不抽象、不设计通用框架。丑是正常的。

## ✅ M2 · 世界变真 · 3.5 天

**🎯 解锁**：agent 面对的不再是一个服务和一堆日志，而是**三个互相调用的服务 + 五类数据**

**覆盖需求**：FR-1、FR-15

| 任务 | 内容 | 状态 |
| ---- | ---- | ---- |
| FIV-6 | 扩展到 3 个服务（order / payment / inventory）+ 调用依赖 | ✅ |
| FIV-7 | 生成指标数据（QPS / 错误率 / P95） | ✅ |
| FIV-8 | 加配置文件与发布历史 | ✅ |
| FIV-9 | 定义**场景包**落盘格式（`question` + `data` + `ground_truth`） | ✅ |

**交付物**：`fivewhys build-scenario` 一条命令导出完整场景包 ✅

**验收**：3 个服务互相调用 ✅；日志 / 指标 / 配置三类数据都能查 ✅；
场景包能独立加载并复现 ✅

> **已完成。** 数据层五类齐备：日志、指标、配置、发布、拓扑。
> 「可查」目前指数据仓库可直接查询；**给 agent 用的查询工具在 M4**。

> 💡 本阶段最有价值的产出是**证据链完整**：指标发现异常 → 日志给出时间点
> → 配置暴露根因 → 发布排除干扰。四步走完根因明确，这正是 agent 要复现的推理过程。
>
> 另一条关键设计：**答案在配置里，不在日志里**。
> 日志是现象（一搜就全看见），配置是证据（必须先怀疑到才会去查）。
> 把 `pool_size` 写进日志，这个场景就没难度了。

## ✅ M3 · 故障库 · 2.5 天

**🎯 解锁**：5 种不同故障 + **会测 agent 会不会无中生有**

**覆盖需求**：FR-2、FR-4

| 任务 | 内容 | 状态 |
| ---- | ---- | ---- |
| FIV-10 | 抽出统一的注入器接口（现在才做抽象，不早不晚） | ✅ |
| FIV-11 | 再实现 4 种故障（共 5 种）+ **正常场景**（`NO_FAULT`） | ✅ |
| FIV-12 | 场景快照脚本（保证可复现） | ✅ |

**交付物**：`fivewhys build-scenario --category <fault_name>` 5 种故障都能注入
（另有 `fivewhys faults` 列清单、`python scripts/snapshot_scenarios.py` 拍快照）

**验收**：5 种故障的日志里**都不得出现** `GroundTruth.match_keywords` 里的任何词；
正常场景（`NO_FAULT`）不产生任何 ERROR/WARN

> **已完成。** 5 种故障 + 1 个健康对照全部通过 `Scenario.validate()`；
> `eval/scenario_snapshot.json` 把评测集的字节级指纹提交进了版本库，
> `fivewhys snapshot --check` 能证明「同一份代码 + 同一个种子 → 同样的字节」。
>
> 💡 「正常场景」是 §10.2 的要求。如果评测集全是"有故障"的场景，
> agent 会养成"无论如何都要编一个根因"的坏习惯。
>
> 💡 FIV-12 顺手修掉一个**跨平台不可复现**的真问题：Windows 上 `open("w")`
> 默认把 `\n` 写成 CRLF，同一份数据在两台机器上指纹不同。
> 场景包现在强制 LF —— 否则「可复现」只是「在我机器上可复现」。

## ✅ M4 · 工具补齐 · 2 天

**🎯 解锁**：agent 有 5 件工具，能像 SRE 一样按路径查数据

**覆盖需求**：FR-5、NFR-11

| 任务 | 内容 | 状态 |
| ---- | ---- | ---- |
| FIV-13 | 补齐 5 个工具：日志 / 指标 / 配置 / 发布 / 依赖 | ✅ |
| FIV-14 | 工具描述打磨（这是 prompt 工程的核心） | ✅ |
| FIV-15 | 每个工具的单测 | ✅ 并入 FIV-13/14 |

**交付物**：`ToolRegistry` 里有 5 个工具，每个都有单测

**验收**：每个工具返回 ≤ 2000 token（NFR-11）；工具描述能说清"什么场景该用它"

> **已完成。** FIV-13 把 5 个工具按「一次真实排障的先后」注册：
> 指标（有没有问题、从什么时候）→ 日志（具体报错）→ 配置（改了什么）→
> 发布（找嫌疑/排除嫌疑）→ 拓扑（症状在上游时往下追）。
> FIV-14 把说明书补齐成「位置 / 局限 / 典型调用」三件套，并给总量设了预算
> （2167 字 ≈ 722 token / 次请求，每次都发，直接落在 NFR-2 上）。
>
> 手工验证的门槛是**不看 LLM，只看工具返回**：
> `python scripts/inspect_scenario.py` 会把 5 个工具的原始输出打出来。
> 实测能从「14:02 起错误率 13%、P95 3055ms」一路走到
> 「14:01:58 `db.pool_size: 50 -> 5`」—— 而日志里从头到尾没有答案词。
>
> 💡 两处「静默地把错误当成结论」的坑，都是手工看输出才发现的：
> 服务名写错时返回的「查不到」会被当成排除性证据；
> `levels=["warning"]` 会被过滤成 0 条、看起来像「服务健康」。
> 现在前者会明确指出服务名不对，后者会直接报错。
>
> ⚠️ 这 5 个工具是**按数据源切分**的，是 M7 A/B 实验的**对照组**。
> 见需求 §5 FR-5 的设计假设。
