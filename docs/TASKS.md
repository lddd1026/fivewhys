### 缺陷（发现问题立刻记录，不夹带在别的任务里）

- [x] **FIV-D2** `.env` 里的 provider key 根本没进进程环境 · ✅ 已完成
  - **发现方式**：第一次拿真实 key 跑 demo —— `fivewhys doctor` 显示
    「未设置 DEEPSEEK_API_KEY」，而 `.env` 明明就在那儿
  - **原因**：`SettingsConfigDict(env_file=".env")` **只服务它自己的字段**
    （`FIVEWHYS_*` 那些）。`DEEPSEEK_API_KEY` 不是 Settings 的字段 ——
    它是 **litellm 从 `os.environ` 里读的**。而全项目没有任何地方调 `load_dotenv()`：
    `python-dotenv` 自 M0 起就写在依赖里，却从来没被 import 过
  - **后果**：README / DEV 里那句「`cp .env.example .env` 然后填上 key」
    **是条死路** —— key 被静默忽略，用户会收到一个莫名其妙的鉴权失败。
    直接违反 G4（陌生人 5 分钟内跑出结果）
  - **修法**：`config.py` 在构造 Settings 之前 `load_dotenv(override=False)`。
    真实环境变量优先于 `.env`（CI 凭据、临时导出的变量都该赢）
  - **为什么离线测试全绿也没发现**：测试全都直接 `monkeypatch.setenv` 设环境变量，
    从来不经过 `.env` 这条路。**只有真按用户的步骤走一遍才会撞上。**
    现在补了两个子进程测试，精确复现「一个放着 .env 的目录 + 跑 python」

- [x] **FIV-D1** 故障期间下游服务**完全没有流量** · ✅ 已完成
  - 提交：`50af7c1 fix(mock): 故障期间的背景流量改走完整调用链`
  - **证据**（FIV-13 手工检查工具输出时发现）：

    ```
    故障窗口 14:02:00 ~ 14:07:00
    order-service      故障期 5 桶 ['14:02','14:03','14:04','14:05','14:06']
    payment-service    故障期 0 桶 []
    inventory-service  故障期 0 桶 []
    ```

  - **原因**：`FaultScript.background_traffic()` 只给**自己这个服务**发正常流量，
    没有走拓扑（对比 `healthy.py` 用的是 `system.emit_request()`，是跨服务的）
  - **为什么是 P0**：这不只是「不够真」——**它是一种泄漏**。
    故障场景的下游没流量、健康场景有，于是 agent 只要查一次下游服务的指标
    就能判断「有没有故障」，完全不需要推理。而且 `dependency_5xx` 场景本来就
    要 agent 顺着调用链往下查，下游却查不到任何流量 —— 核心手法被抽掉了
  - **修法**：`FaultScript` 拿得到 `system`，背景流量改走
    `system_traffic()` → `MockSystem.emit_request()`，跨服务生成；
    拿不到 system 时（M1 的单服务用法）自动退化成原来的单服务噪声
  - **效果**：每一种故障的故障窗口里，三个服务都有 5 个指标桶 ——
    和健康场景**完全一致**，从「哪些服务有数据」再也看不出有没有故障。
    实测 `dependency_5xx`：inventory-service（真正的根因）现在有 5 个桶、
    16.7% 错误率、17 条 WARN/ERROR 日志，调用链排查这条路通了
  - **验收**：13 个新测试（含按类别参数化的「每个服务都要有流量」、
    「故障场景和健康场景的流量分布必须一样」），全套 378 passed
  - **重拍了快照**：`4a093df4` → `c38b322b`（5 个故障场景全变，
    `no_fault` 纹丝不动 —— 说明改动正好只影响了该影响的地方）。
    这正是 FIV-12 那道闸门存在的意义：改了评测集，必须先承认

## FIV-5 · 端到端验证 M1 ← 当前任务

**优先级** `P0`　**预估** 2h（实际只差真实模型的 5 次运行）　**分支** 已完成

### 背景

M1 的验收标准是一条**数字**：给 agent 一个连接池耗尽的场景，跑 5 次至少 3 次对。
在线能做的都做完了 —— 脚本、判分、假 LLM 链路、完整证据链、离线可看性。
剩下的只有一件事：**真实模型跑一遍**。

### 为什么不能糊弄过去

「跑 5 次至少 3 次正确」这句话将来要写进 README，是面试时最容易被追问的数字。
用假 LLM 跑出来的「通过」只能证明链路通，**证明不了模型够聪明**：
响应是脚本化的，不涉及任何推理。所以这条验收必须由真实模型完成。

### 目标

在 `.env` 里配好 `DEEPSEEK_API_KEY`，跑：

```powershell
.\.venv\Scripts\python.exe scripts/demo_m1.py --runs 5 --trace
```

### 验收标准

- [ ] 输出表格里 5 行得分，至少 3 行 ≥ 80%
- [ ] 末行打印「M1 验收通过」，退出码 0
- [ ] 记录总成本（NFR-2 的单次上限是 $0.10）
- [ ] 把这张表贴进本文件 + `README.md` 的评测结果表
- [ ] 顺带看一眼 `--trace`：模型**真的**用了几个工具、有没有走错路

### 如果没过（很可能第一次过不了）

这不算失败，**这正是项目剩下的全部价值所在**。按顺序看：

1. 它卡在哪一步？（`--trace` 里最后一次工具调用是什么）
2. 是没提交结论（`max_steps`）？还是提交了但根因错？
3. 把失败样本记下来 —— 这就是 M7「改进迭代」要优化的东西，
   也是 README 里那条「从 X% 到 Y%」曲线的基线

   以及「哪些结论**不能**由离线实验得出」）

## FIV-1 · 实现 `db_pool_exhausted` 故障注入（已归档）

**优先级** `P0`　**预估** 2h　**分支** `feat/FIV-1-inject-db-pool`

### 背景

我们需要一个「会坏」的假系统，让 agent 有东西可诊断。

关键在于 **ground truth 必须由我们掌握**——用真实系统就没法知道正确答案，
没有正确答案就没有自动判分，整个项目会退化成 demo。

### 目标

让 `inject_db_pool_exhausted()` 能往日志里注入一组**只反映现象、不暴露答案**的记录。

### 要做的事

1. 读 `src/fivewhys/mock/scenarios.py` 头部注释，里面写了完整的日志规格
2. 实现 `inject_db_pool_exhausted()`，按时间顺序写入 4 类日志：
   - 配置重载（INFO，触发点）
   - 错误开始出现（ERROR，逐渐变密）
   - 连接等待时间飙升（WARN，指向连接池的关键线索）
   - 请求延迟超 SLO（WARN，稀疏）
3. 返回填好的 `GroundTruth`
4. 把 `tests/test_smoke.py::test_inject_db_pool_exhausted_not_implemented_yet`
   改成真正的断言

### 验收标准

- [ ] 文件末尾的自测命令能跑通，打印出 `GroundTruth` 和日志统计
- [ ] `store.stats()` 里 ERROR 数量在 **10~30** 之间
- [ ] 日志里**不出现** `pool` / `连接池` / `exhaust` 字样
- [ ] 时间戳严格递增
- [ ] 同样的输入跑两次，输出的日志完全一致（可复现）
- [ ] `pytest` 全绿

### 提示

- 用 `service.emit(level, message, ts)` 写日志
- 用 `service._rng` 取随机数，**不要用全局 `random`**——否则场景不可复现
- 时间要错开：配置重载必须**严格早于**错误开始出现

### 自查问题（提交前问自己）

1. 如果我是 agent，只看这些日志，能直接读出答案吗？能 → 说明写太直白了，重写。
2. 这些日志混在正常请求日志里，显眼吗？太显眼 → 说明噪声不够。
