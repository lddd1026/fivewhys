## 1. 背景与问题

### 1.1 直接动因

作者需要求职 **agent 应用开发**方向的岗位，需要一个能证明能力的个人项目。

### 1.2 为什么不做"求职 agent"

市面上已经饱和：

| 项目 | Star | 状态 |
| ---- | ---- | ---- |
| career-ops | 70.8k | 已把这个题的"标准答案"写完了 |
| AIHawk | 原 30k+ | 已转型，不再做自动投递 |
| 同类小项目 | 十余个 | jobclaw / AutoApply / ai-job / autopilot-jobhunt … |

再做一个，面试官的第一反应是"抄的"或"跟着教程做的"，且这类项目的技术难点在爬虫和反爬，
与 agent 工程能力关系不大，还有合规风险。

### 1.3 为什么选"故障根因诊断"

| 标准 | 是否满足 |
| ---- | -------- |
| 痛点普适，面试官一听就懂 | ✅ 线上故障排查是通用痛点 |
| 单次 LLM 调用无法解决（天然多步） | ✅ 必须查多个数据源再推理 |
| 可造出客观标准答案 | ✅ 故障由我们注入 |
| 有工具设计空间 | ✅ 工具怎么切分直接影响成败 |
| 生态里还没有标准答案 | ✅ 与 faultline / whatbroke 方向不同，详见 README |

## 2. 目标

| 编号 | 目标 | 判定方式 |
| ---- | ---- | -------- |
| **G1** | 能力：构建一个能对模拟线上故障做**多步根因诊断**的 agent | 根因定位准确率显著优于 baseline |
| **G2** | 证据：产出一组**可信、可复现**的量化指标 | 任何人按 README 操作能得到相同数字 |
| **G3** | 展示：体现 agent 应用开发的四项核心能力 | 见下方 3.1 |
| **G4** | 可复现：陌生人能在 5 分钟内跑出结果 | 请一位朋友实测 |

### 2.1 G3 要展示的四项能力

这是本项目的**真正目的**——G1 和 G2 都是手段。

| 能力 | 在项目里体现在哪 |
| ---- | ---------------- |
| **工具设计** | 工具按 SRE 排障路径切分，而非按数据源切分；M7 用数据验证这个决策 |
| **多步编排** | agent 循环、终止条件、失败重试、上下文管理 |
| **结构化输出** | 用 Pydantic 约束 `Diagnosis`，并校验证据来源真实性 |
| **评测能力** | 自建评测台、失败分类、改进曲线（这是绝大多数人没有的） |

## 3. 非目标

**明确不做。** 写下来是为了防止范围蔓延——需求文档最常见的失败是"什么都想要"。

| 编号 | 不做 | 原因 |
| ---- | ---- | ---- |
| NG-1 | 生产可用的监控/诊断系统 | 这是求职项目，不是产品 |
| NG-2 | 接入真实系统 | 无法掌握 ground truth，评测无从谈起 |
| NG-3 | 自动修复（只诊断，不动手） | 风险高、无 ground truth、偏离展示重点 |
| NG-4 | Web 前端 / 可视化大盘 | 面试官看**指标表**，不看 UI |
| NG-5 | 多租户、权限、部署、K8s | 与 agent 工程能力无关 |
| NG-6 | 爬取任何真实网站 | 合规风险；且故障场景是自造的 |

## 5. 功能需求

状态：`✅ 已实现` · `🟡 部分实现` · `⬜ 未实现`

### FR-1 模拟系统 `🟡`

系统应能生成一个**包含多个服务**的模拟环境，每个服务持续产生结构化日志。

- M1：1 个服务 + 日志 ✅
- M2：3 个服务 + 调用依赖 + 指标 + 配置 + 发布历史 ⬜

### FR-2 故障注入 `🟡`

系统应能对模拟系统注入故障。**注入的痕迹只能通过"现象"观察，不得直接暴露根因。**

- **判据（可自动检查）**：注入产生的日志文本中，不得出现根因关键词
- M1：1 种故障 ✅
- M3：5 种 🟡 → M8：20 种 ⬜

### FR-3 标准答案 `✅`

每次故障注入必须同时产出 `GroundTruth`：根因服务、故障类别、根因描述、判分关键词。

### FR-4 场景可复现 `✅`

相同的场景标识必须产生**逐字节一致**的模拟数据。所有随机行为由显式种子驱动。

### FR-5 排障工具 `⬜`

系统应向 agent 提供一组**只读**排障工具，覆盖五类数据：

| 工具 | 数据源 | 状态 |
| ---- | ------ | ---- |
| `query_logs` | 日志 | ⬜ FIV-2 |
| `query_metrics` | 指标 | ⬜ FIV-13 |
| `get_config` | 配置 | ⬜ FIV-13 |
| `get_deploy_history` | 发布记录 | ⬜ FIV-13 |
| `get_dependencies` | 服务依赖 | ⬜ FIV-13 |

**设计原则**：按 **SRE 的真实排障路径**切分，而非按数据源切分。

### FR-6 诊断 agent `⬜`

系统应能**多步调用工具**，并输出结构化 `Diagnosis`，包含：根因、根因服务、故障类别、
置信度、5 Whys 追问链、证据列表、被排除的嫌疑、修复建议、给值班工程师的摘要。

### FR-7 终止控制 `⬜`

agent 必须在以下**任一**条件下停止，并记录停止原因：

| 条件 | `stop_reason` |
| ---- | ------------- |
| 提交了诊断 | `submitted` |
| 达到 5 Whys 深度上限 | `max_why_depth` |
| 达到步数上限 | `max_steps` |
| 达到成本上限 | `max_cost` |

5 Whys 深度是**主要**停止条件（有方法论依据），其余是兜底。

### FR-8 证据校验 `⬜`

`Diagnosis` 中的每条 `evidence` 必须能对应到一次**真实的工具调用**。
无法对应的应被拒绝或标记——这是防止模型编造证据的硬约束。

### FR-9 轨迹记录 `⬜`

每次诊断必须落盘完整轨迹：每步的 prompt、模型响应、工具调用与返回、token 数、
成本、耗时。轨迹是 M6/M7 分析失败、产出指标的唯一依据。

### FR-10 评测执行 `⬜`

系统应能对 N 个场景各跑 M 次，**全程无人工干预**，并记录所有 `AgentRun`。

### FR-11 指标计算 `⬜`

系统应能计算四项指标：

| 指标 | 说明 |
| ---- | ---- |
| 根因定位准确率 | **核心指标** |
| 平均工具调用次数 | 体现工具设计与效率 |
| 平均成本（$） | 工程约束 |
| P95 延迟 | 工程约束 |

**后三项是防止刷分的约束**：只报准确率没有意义，多跑几次总能碰对。

### FR-12 对比报告 `⬜`

系统应能输出多个版本的指标对比表，用于生成"改进曲线"（即 M7 的产出）。

### FR-13 响应缓存 `⬜`

重复的 LLM 请求应命中缓存，使评测在**零增量成本**下可重复运行。

### FR-14 可复现性（面向 U2）

- **FR-14a 离线自检** `✅`：无需 API Key 即可跑通测试与 `fivewhys doctor`
- **FR-14b 快速上手** `⬜`：有 API Key 时，5 分钟内跑出评测结果（含 Docker 一键启动）

## 8. 度量指标（简历数字的来源）

| 指标 | 定义 | 目标 |
| ---- | ---- | ---- |
| **根因定位准确率** | 结论命中的场景数 ÷ 总场景数 | baseline 越低越好（说明有提升空间）；最终争取 > 80% |
| 平均工具调用次数 | 单次诊断的工具调用数 | 越低越好 |
| 平均成本 | 单次诊断的 API 费用 | ≤ $0.05 |
| P95 延迟 | 单次诊断耗时 | ≤ 60s |
| **提升幅度** | final − baseline | **这是简历上的主数字** |

### 8.1 简历上那句话的模板

> 构建可注入 N 类故障的微服务模拟环境，设计 M 个排障工具，实现多步诊断 agent；
> 通过工具粒度优化与结构化输出约束，将根因定位准确率从 **X%** 提升至 **Y%**，
> 平均工具调用次数从 **A** 次降至 **B** 次，单次诊断成本 **$C**。

**X 越低越好。** 所以 M6 跑出来的 baseline 如果高于 90%，说明故障设计太简单，要回 M3 加强。
