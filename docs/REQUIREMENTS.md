## 1. 背景与问题

### 1.1 直接动因

作者需要求职 **agent 应用开发**方向的岗位，需要一个能证明能力的个人项目。

### 1.2 为什么不做"求职 agent"

市面上已经饱和：

| 项目 | Star | 状态 |
| ---- | ---- | ---- |
| career-ops | 70.8k | 已把这个题的"标准答案"写完了 |
| AIHawk | 原 30k+ | 已转型，不再做自动投递 |
| 同类小项目 | 十余个 | jobclaw / AutoApply / ai-job / autopilot-jobhunt … |

再做一个，面试官的第一反应是"抄的"或"跟着教程做的"，且这类项目的技术难点在爬虫和反爬，
与 agent 工程能力关系不大，还有合规风险。

### 1.3 为什么选"故障根因诊断"

| 标准 | 是否满足 |
| ---- | -------- |
| 痛点普适，面试官一听就懂 | ✅ 线上故障排查是通用痛点 |
| 单次 LLM 调用无法解决（天然多步） | ✅ 必须查多个数据源再推理 |
| 可造出客观标准答案 | ✅ 故障由我们注入 |
| 有工具设计空间 | ✅ 工具怎么切分直接影响成败 |
| 生态里还没有标准答案 | ✅ 与 faultline / whatbroke 方向不同，详见 README |

## 2. 目标

| 编号 | 目标 | 判定方式 |
| ---- | ---- | -------- |
| **G1** | 能力：构建一个能对模拟线上故障做**多步根因诊断**的 agent | 根因定位准确率显著优于 baseline |
| **G2** | 证据：产出一组**可信、可复现**的量化指标 | 任何人按 README 操作能得到相同数字 |
| **G3** | 展示：体现 agent 应用开发的四项核心能力 | 见 §2.1 |
| **G4** | 可复现：陌生人能在 5 分钟内跑出结果 | 请一位朋友实测 |

### 2.1 G3 要展示的四项能力

这是本项目的**真正目的**——G1 和 G2 都是手段。

| 能力 | 在项目里体现在哪 |
| ---- | ---------------- |
| **工具设计** | 有一个明确的切分假设，并用 A/B 实验验证（见 FR-5、§10.3） |
| **多步编排** | agent 循环、终止条件、失败重试、上下文管理 |
| **结构化输出** | 用 Pydantic 约束 `Diagnosis`，并校验证据来源真实性 |
| **评测能力** | 自建评测台、判分规则、失败分类、改进曲线（绝大多数人没有这个） |

## 5. 功能需求

状态：`✅ 已实现` · `🟡 部分实现` · `⬜ 未实现`

### FR-1 模拟系统 `🟡`

系统应能生成一个**包含多个服务**的模拟环境，每个服务持续产生结构化日志。

- M1：1 个服务 + 日志 ✅
- M2：3 个服务 + 调用依赖 + 指标 + 配置 + 发布历史 ⬜

### FR-2 故障注入 `🟡`

系统应能对模拟系统注入故障。**注入的痕迹只能通过"现象"观察，不得直接暴露根因。**

- **判据（可自动检查）**：注入产生的日志文本中，不得出现 `GroundTruth.answer_keywords` 里的任何词
  > ⚠️ 注意是 `answer_keywords`，**不是** `match_keywords`。两者用途不同，见 FR-3。
  > 用错会导致「关键线索被误判成泄漏」—— 这个坑在 FIV-5 踩过。
- M1：1 种故障 ✅
- M3：5 种 🟡 → M8：20 种 ⬜

### FR-3 标准答案 `✅`

每次故障注入必须同时产出 `GroundTruth`：根因服务、故障类别、根因描述、判分关键词、
注入时间点、表面症状。

**判分方式见 §6。**

### FR-4 场景可复现 `✅`

相同的场景标识必须产生**逐字节一致**的模拟数据。所有随机行为由显式种子驱动。

**判据（可自动检查）**：`fivewhys snapshot --check` 用当前代码 + 同一种子
重造全部场景，逐文件比对 SHA-256；有任何一处不一致就退出码 1 并指出是哪份文件。

指纹清单提交在 `eval/scenario_snapshot.json`。场景包本身（`data/scenarios/`）是生成物，
在 `.gitignore` 里 —— 它能随时重造，但**指纹必须进版本库**，否则没人能判断
「这次跑的场景和上次是不是同一套」。

> 为什么这事重要：M7 的改进曲线只有在「两次跑的是同一套场景」时才可比。
> 注入器里改一行日志条数，diff 看起来无关紧要，但评测集已经变了。
> 指纹一红，就必须先承认这件事。
>
> 实现时发现一个真问题：Windows 上 `open("w")` 默认把 `\\n` 写成 CRLF，
> 同一份数据在两台机器上指纹不同 —— 场景包现在强制 LF（见 §12.3）。

### FR-5 排障工具 `🟡`

> 5 个工具已全部实现并有测试覆盖（FIV-2 / FIV-13）；
> 剩下的 🟡 是「按 SRE 路径切分是否更好」这个假设还没验证 —— 那是 M7 的 A/B 实验。

系统应向 agent 提供一组**只读**排障工具。工具集合见下表。

| 工具 | 数据源 | 里程碑 | 状态 |
| ---- | ------ | ------ | ---- |
| `query_logs` | 日志 | M1 | ✅ FIV-2 |
| `query_metrics` | 指标 | M4 | ✅ FIV-13 |
| `get_config` | 配置 | M4 | ✅ FIV-13 |
| `get_deploy_history` | 发布记录 | M4 | ✅ FIV-13 |
| `get_dependencies` | 服务依赖 | M4 | ✅ FIV-13 |

**共同约定**（5 个工具一致，由 :mod:`fivewhys.tools._render` 统一实现）：

- 返回**给模型读的文本**，不是给程序读的 JSON：第一行是结论，然后是元信息，再是明细
- 受 NFR-11 预算约束（约 6000 字符），超了要**明说被截断了**
- **空结果必须给出下一步线索** ——「无数据」三个字会让模型以为工具坏了，
  然后放弃这条最有价值的路径
- **服务名写错时必须明确指出**，并列出这个场景里真实存在的服务。
  否则一次笔误返回的「查不到」会被当成一条排除性证据 —— 这是 FIV-13 手工验证时
  想清楚的一个坑

**说明书的写法**（FIV-14 定的规矩，每条都有测试守着）：

- 必须写清**位置**：它在排障路径上是第几步（不属于任何一步的必须明说）。
  ⚠️ **只能有一个「第一步」** —— FIV-14 通读时发现 `query_metrics` 和
  `query_logs` 都写着自己才是第一步，两个都说是等于都没说
- 必须写清**局限**：什么时候不该用它、它查不到什么。
  「能干什么」模型猜得出来，「查不到什么」猜不出来，而走错路的代价更大
- 必须给一条**典型调用**，把参数形态摆出来（时间是 ISO 8601 还是时间戳？
  服务名是短名还是全名？）—— 一条例子比三段解释省字
- 不许出现「之类」「等等」这类含糊词：给人看没问题，给模型看就是噪声
- **总量有预算**（`TOOL_DESCRIPTION_BUDGET_CHARS = 3000` 字符）。
  说明书写在每一次请求的提示词里，30 步的诊断就发 30 遍 ——
  这笔钱直接落在 NFR-2 上。超预算时该删废话，而不是调高数字
- 枚举值必须**内联**在 schema 里（不用 `$ref`），并且**写错要报错**：
  参数写错时静默返回空，等于把一次笔误变成一条「服务是健康的」结论

#### 设计假设（重要）

> **假设**：按 **SRE 的真实排障路径**切分工具，比按**数据源**切分更有效。
>
> **现状**：上表是**按数据源切分**的——这是 M1~M4 的对照组实现，不是最终形态。
>
> **验证**：M7 用一个 A/B 实验对比两个变体（见 §10.3）：
>
> | 变体 | 工具设计 |
> | ---- | -------- |
> | A（对照组） | 5 个按数据源切的工具 |
> | B（实验组） | 3 个按排障路径切的工具，例如 `check_recent_changes`（同时看发布与配置）、`trace_request`（追一次请求的完整链路） |
>
> **结论无论正反都有价值**：假设成立 → 证明设计能力；假设不成立 → 证明会用数据证伪自己的假设。
> 两种结果都是好的面试素材。

### FR-6 诊断 agent `⬜`

系统应能**多步调用工具**，并输出结构化 `Diagnosis`，包含：根因、根因服务、故障类别、
置信度、5 Whys 追问链、证据列表、被排除的嫌疑、修复建议、给值班工程师的摘要。

**`confidence` 字段的用途**：仅作展示和信息传递，**不参与判分**。
它的价值是让 `Diagnosis` 看起来像一个真实的工程产物，而不是冷冰冰的判定。

### FR-7 终止控制 `⬜`

agent 必须在以下**任一**条件下停止，并记录 `stop_reason`：

| 条件 | `stop_reason` | 地位 |
| ---- | ------------- | ---- |
| 提交了诊断 | `submitted` | **正常路径** |
| 达到 5 Whys 深度上限 | `max_why_depth` | 主要停止条件（有方法论依据） |
| 达到步数上限 | `max_steps` | 兜底 |
| 达到成本上限 | `max_cost` | 兜底 |
| 运行异常 | `error` | 异常 |

**各种停止情形如何计入准确率，见 §6.2。**

### FR-8 证据校验 `⬜`

`Diagnosis` 中的每条 `evidence` 必须能对应到一次**真实的工具调用**。
无法对应的应被拒绝或标记——这是防止模型编造证据的硬约束。

### FR-9 轨迹记录 `🟡`

每次诊断必须落盘完整轨迹：每步的 prompt、模型响应、工具调用与返回、token 数、
成本、耗时。轨迹是 M6/M7 分析失败、产出指标的唯一依据。

### FR-10 评测执行 `⬜`

系统应能对 **N 个场景各跑 M 次**，全程无人工干预，并记录所有 `AgentRun`。

**基线取值**：

| 参数 | 值 | 理由 |
| ---- | -- | ---- |
| N | M6 先用 **10**，M8 补到 **20** | 先跑通再扩充 |
| M | **5** | 5 次能区分"稳定失败"与"偶发失败"；再多成本翻倍但信息增量有限 |

N 和 M 一经确定，**同一轮对比中不得更改**——否则指标不可比。

### FR-11 指标计算 `⬜`

系统应能计算五项指标：

| 指标 | 说明 |
| ---- | ---- |
| **根因定位准确率** | **核心指标**（定义见 §6） |
| 误报率 | 正常场景里被错误报出故障的比例 |
| 平均工具调用次数 | 体现工具设计与效率 |
| 平均成本（$） | 工程约束 |
| P95 延迟 | 工程约束 |

**误报率**必须单独报，因为它是"正常场景"（见 §10.1）的唯一产出。
**其余三项是防止刷分的约束**：只报准确率没有意义，多跑几次总能碰对。

### FR-12 对比报告 `⬜`

系统应能输出多个版本的指标对比表，用于生成"改进曲线"（见 §10.3）。

### FR-13 响应缓存 `⬜`

重复的 LLM 请求应命中缓存，使评测在**零增量成本**下可重复运行。

### FR-14 可复现性（面向 U2）

- **FR-14a 离线自检** `🟡`：无需 API Key 即可跑通测试与 `fivewhys doctor` ✅；
  另需 `fivewhys demo --offline`——不调用任何 LLM，直接展示"注入故障后的模拟系统长什么样" ⬜
- **FR-14b 快速上手** `⬜`：有 API Key 时，5 分钟内跑出评测结果（含 Docker 一键启动）

### FR-15 场景包 `🟡`

> 落盘 / 独立加载 / 可复现三件事**已完成并有测试覆盖**（FIV-9、FIV-12）；
> 剩下的 🟡 是「在评测里被验证」—— 按 §11.1 的标准要等 M6 的评测台跑起来。

每个评测场景由三部分组成，必须**整体落盘**、可独立加载、可复现：

| 组成 | 内容 | agent 可见性 |
| ---- | ---- | ------------ |
| `question` | 现象描述，agent 收到的初始输入 | ✅ 可见 |
| `data` | 模拟数据（日志 / 指标 / 配置 / 发布 / 依赖） | ✅ 通过工具查 |
| `ground_truth` | 标准答案 | ❌ **不可见** |

#### question 规格（决定任务难度）

模板：

```
{service} 从 {time} 前后开始 {symptom}，帮忙定位一下原因
```

示例：

```
order-service 从 14:30 前后开始错误率飙升，帮忙定位一下原因
```

| 提供 | 不提供 |
| ---- | ------ |
| ✅ 服务名 | ❌ 具体错误信息 |
| ✅ 粗略时间（±5 分钟） | ❌ 精确时间窗口边界 |
| ✅ 表面症状（错误率 / 延迟） | ❌ 根因、故障类别、受影响的其它服务 |

**判据（可自动检查）**：`question` 文本中不得出现 `GroundTruth.match_keywords` 里的任何词。

#### 正常场景的 question

```
order-service 今天 14:00 前后有用户反馈下单偶尔变慢，帮忙确认一下是否有问题
```

其 `ground_truth` 标记为 `FaultCategory.NO_FAULT`（**需在枚举中新增该值**）。

## 6. 判分规则

> 这一节定义**"答对了"是什么意思**。它是 FR-11 核心指标的计算依据。
> 判分规则不清晰，跑出来的数字就没有意义。

### 6.1 判定项与权重

一次诊断的判定由三项组成：

| 判定项 | 比对方式 | 权重 |
| ------ | -------- | ---- |
| **根因服务** | `Diagnosis.root_cause_service` **精确字符串匹配** `GroundTruth.root_cause_service` | 40% |
| **故障类别** | `Diagnosis.fault_category` **枚举精确匹配** `GroundTruth.fault_category` | 40% |
| 根因描述 | 关键词命中（见下方约束） | 20% |

**总分 ≥ 80% 记为「判定为对」。**

#### 为什么主要靠前两项

我们有 `FaultCategory` 枚举和明确的服务名——**本来就是结构化的，就该用精确匹配**。
它是确定性的、可复现的、经得起追问的。关键词匹配只做兜底。

#### 关键词匹配的约束

关键词**只在 `Diagnosis.root_cause` 和 `Diagnosis.summary` 两个字段里扫描**。

**绝不能扫描 `ruled_out`** —— 否则 agent 写"我排除了连接池问题"，会因为出现"连接池"
而被误判为命中。这是最容易写错的一处。

### 6.2 结果分类与分母

| 结果 | `stop_reason` | 有 `diagnosis` | 计入分母 | 记为 |
| ---- | ------------- | -------------- | -------- | ---- |
| 正常提交 | `submitted` | ✅ | ✅ | 按 §6.1 判 |
| 超深度 | `max_why_depth` | ✅ | ✅ | 按 §6.1 判 |
| 超深度 | `max_why_depth` | ❌ | ✅ | **错** |
| 超步数 | `max_steps` | ✅ | ✅ | 按 §6.1 判 |
| 超步数 | `max_steps` | ❌ | ✅ | **错** |
| 超成本 | `max_cost` | 任意 | ✅ | 有诊断按 §6.1 判，无诊断记错 |
| 运行异常 | `error` | 任意 | ❌ | 单独统计**崩溃率** |

```
准确率 = 判定为对的次数 ÷ 计入分母的次数
崩溃率 = error 次数 ÷ 总运行次数        ← 单独报，不计入准确率
```

**崩溃率单独报的理由**：它反映的是**工程稳定性**，不是诊断能力。
两者混在一起，会让人分不清"agent 笨"和"代码有 bug"。

### 6.3 已知局限与缓解

| 局限 | 缓解 |
| ---- | ---- |
| 关键词匹配会漏判（agent 说"连接数不够"，关键词是"连接池"） | M6 人工抽检 20% 样本，校准关键词表 |
| 部分得分（80% 阈值）是拍的 | 记录原始得分，报告里同时给出「加权平均分」和「判定为对的比例」 |

**关键**：判分不完美没关系。**只要所有对比版本用同一套判分，改进曲线就是可信的。**
这一点必须在 README 里写清楚。

## 7. 非功能需求

| 编号 | 需求 | 判定方式 | 状态 |
| ---- | ---- | -------- | ---- |
| **NFR-1** | 可复现：所有随机行为由显式种子驱动 | 同场景跑两次输出逐字节一致 | ✅ |

| 指标 | 定义 | 目标 |

### 9.1 简历上那句话的模板

> 构建可注入 N 类故障的微服务模拟环境（含 M% 健康场景用于测误报），设计 X 个排障工具，

> 将根因定位准确率从 **X%** 提升至 **Y%**，平均工具调用次数从 **A** 次降至 **B** 次，
> 单次诊断成本 **$C**（模型：`xxx`）。

**X 越低越好。** 所以 M6 跑出来的 baseline 如果高于 90%，说明故障设计太简单，要回 M3 加强。

## 10. 评测集构成

### 10.1 场景分布

| 类型 | 数量 | 说明 |
| ---- | ---- | ---- |
| 单故障 | 12 | 一种故障，根因清晰 |
| 复合故障 | 3 | 两个故障叠加，考察排除能力 |
| **正常场景** | **5** | 系统健康，正确答案是「无故障」 |
| **合计** | **20** | M6 先用其中 10 个（8 故障 + 2 正常）跑通 |

### 10.2 为什么必须有正常场景

如果评测集**全是"有故障"的场景**，agent 会养成一个坏习惯：

> 无论输入什么，都要编出一个根因。

因为训练/提示的环境告诉它"总是有问题的"。**这在实际使用中是灾难性的**——
一个永远报故障的诊断工具没人敢用。

正常场景测的是**误报率**：它会不会无中生有。

**面试价值**（这段话可以直接说）：

> "我不只测它能不能找到故障，还测它**会不会无中生有**——所以评测集里混了 25% 的健康场景。"

### 10.3 改进的测量方式

M7 的四个改进**累积测量**，不是各自独立对比 baseline：

```
baseline               58%
+ 结构化输出约束        74%
+ 失败重试              85%
+ 工具切分 A/B 实验      89%
+ 步数 / 成本熔断        94%
```

**为什么累积**：更符合真实优化过程，也更容易讲清"每一步贡献了多少"。

#### 工具切分的 A/B 实验（FR-5 的验证）

这是需求里**唯一的正式实验**，产出直接支撑 §5 FR-5 的设计假设：

| 变体 | 工具设计 | 预期 |
| ---- | -------- | ---- |
| A（对照组） | 5 个按数据源切的工具 | baseline |
| B（实验组） | 3 个按排障路径切的工具 | 调用次数下降、准确率上升 |

其余三个改进（结构化输出、重试、熔断）不做 A/B，只做累积记录。

### 12.5 NFR-2 的成本必须真的算得出来（FIV-D3 发现）

第一次拿真实 key 跑完 M1 验收（5/5 全对），demo 表格里「总成本 $0.0000」——
看起来像不要钱，实际是**根本没算**。

**根因**：`litellm.completion_cost()` 拿**响应里回的 model 名**去查价格表，
而 provider 回的名字未必等于请求的别名：实测请求 `deepseek/deepseek-chat` 时
DeepSeek 回的是 `model='deepseek-flash'`，查表失败抛
`This model isn't mapped yet`，被 `estimate_cost` 的 `except Exception` 吞掉，
于是每一次调用都记 0。

而 litellm **已经算好了**：`response._hidden_params["response_cost"]`。
它用的是请求时的别名。现在先读它，读不到再退回 `completion_cost`，最后才是 0。

**修法**：见上。另加三个测试，其中一个精确复现线上那次失败。

> 为什么严重：NFR-2 的成本红线、「平均成本 $0.03」这个目标、
> README 里那张表的每一行，全都依赖这个数字。
> **一个假得很好看的数字（$0.0000）比一个明显缺失的数字更危险。**

**同一轮还发现一个更基础的**：`cp .env.example .env` 那条路是死的 ——
`SettingsConfigDict(env_file=".env")` 只服务 `FIVEWHYS_*` 自己的字段，
而 `DEEPSEEK_API_KEY` 是 litellm 从 `os.environ` 读的，全项目没人调
`load_dotenv()`（`python-dotenv` 自 M0 就写在依赖里，从没被 import 过）。
key 被静默忽略，用户收到的是一句莫名其妙的鉴权失败。见看板 FIV-D2。

> 这两个缺陷有同一个特征：**离线测试全绿，只有真按用户的步骤、拿真 key 跑一次
> 才会暴露**（假 LLM 服务返回的 usage 同样算不出成本）。
> 「离线能验证的」和「必须真跑一次的」之间的那道缝，就是它们藏身的地方。
### 12.4 背景流量必须跨服务（FIV-D1 发现）

**问题**：注入故障时，背景「正常流量」只发给**被注入故障的那个服务**，
而健康场景（`healthy.py`）用的是跨服务的 `system.emit_request()`。实测：

```
故障窗口 14:02:00 ~ 14:07:00
order-service      故障期 5 个指标桶
payment-service    故障期 0 个指标桶
inventory-service  故障期 0 个指标桶
```

**后果有两个，第二个更严重**：

1. 数据不真实 —— 故障期间下游服务其实照常有流量。
2. **这是一条可被利用的泄漏。** 故障场景的下游「没数据」、健康场景「有数据」，
   于是 agent 只要查一次下游服务的指标，就能判断这个场景**有没有故障**，
   完全不需要任何推理。而 `dependency_5xx` 场景的全部难度就在于
   「症状在上游、根因在下游，要顺着调用链追」—— 下游查不到流量，
   这条路直接走不通。

**修法**：`FaultScript` 拿到 `system`，背景流量改走
`system_traffic()` → `MockSystem.emit_request()`，与 `healthy.py` 统一。
拿不到 `system` 时（M1 的单服务最小场景）保留原来的单服务噪声。

**判据（可自动检查）**：对**每一种**故障，故障窗口内每个服务都必须有采样；
且故障场景与健康场景的「哪些服务有流量」必须完全一致。

> 这个缺陷是 FIV-13 手工检查工具输出时发现的，不是测试发现的 ——
> 单看故障场景一切正常，**和健康场景一比才露馅**。
> 修完必须重拍场景快照（§12.3 的闸门），这也正好验证了那个机制有用：
> 它准确报出「5 个故障场景的 logs/metrics 变了，no_fault 没变」。

### 12.3 场景包的换行符与「自我验证」（FIV-12 发现）
**问题一：跨平台不可复现。**

`open("w")` 在 Windows 上默认把 `\n` 转成 CRLF。实测生成的 `logs.jsonl`
2177 行**全是 CRLF** —— 于是同一份数据在 Windows 和 Linux 上算出的 SHA-256 不同。
「可复现」退化成了「在我机器上可复现」。

**修法**：场景包落盘一律 `newline="\n"`。指纹必须跨平台一致，否则它证明不了任何事。

**问题二：校验器自己不可信。**

快照文件里存了两层指纹：总指纹 + 逐文件指纹（用于指出「变的是哪份文件」）。
手工篡改一份副本时发现：只改逐文件指纹、不改总指纹，校验**照样通过**
—— 因为比对的是总指纹。危害不在于漏掉了篡改，而在于从此报错会指错地方。

**修法**：校验前先查快照文件自洽 —— 逐文件指纹必须能加回总指纹，否则直接报
「快照文件自身不一致」。**一个自己不可信的校验器比没有校验器更糟。**

> 这两个坑和 §12.2 是同一类：**结构对、语义错**。
> 单元测试全绿，只有把真实产物打开看一眼才会发现。

### 12.2 关键词清单拆分（FIV-5 离线验证发现）

**问题**：`match_keywords` 原先同时承担两个职责，导致自相矛盾。

| 用途 | 需要的行为 |
| ---- | ---------- |
| 判分（agent 的答案里有没有这些词） | 越宽越好 |
| 查泄漏（日志里不能出现这些词，FR-2） | 越窄越好 |

而 `connection` 是**关键线索**（`connection wait time` 飙升），**必须出现在日志里**。
它一旦进入"查泄漏"清单，日志就会被误判为泄漏 —— 离线验证时确实报了假警报。

**修法**：拆成两份清单。

| 字段 | 用途 | 内容 |
| ---- | ---- | ---- |
| `match_keywords` | 判分（§6.1 的 20% 分项） | 可以宽，含现象词 |
| **`answer_keywords`** | **FR-2 的泄漏判据** | **只含答案词**（pool / 连接池 / 耗尽） |

**连带改动**：
- `GroundTruth` 新增 `answer_keywords` 字段
- FR-2 的判据从 `match_keywords` 改为 `answer_keywords`
- 测试增加**反向检查**：关键线索必须出现（否则 agent 无从推理）
- demo 脚本同时显示两份清单，让用途差异可见

**教训**：一个字段承担两个语义相反的职责，是一定会出问题的。
