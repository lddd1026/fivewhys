# M1 · agent 循环怎么实现

**决策影响**：这是整个项目最核心的一处技术选择，直接决定面试时你能讲多深。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 手写循环**<br>`litellm` + 一个 `while` | · 每一步都在你手里，**面试时能逐行讲清楚**<br>· 无框架依赖，安装快<br>· 会真实暴露 JSON 解析失败、工具报错这些问题——**而这些正是项目要展示的东西**<br>· 代码量小，约 150 行 | · 边界情况要自己处理（重试、消息格式、并发）<br>· 没有现成的可视化调试<br>· 要先搞懂 OpenAI function calling 的消息格式 |
| **B LangGraph** | · 状态机显式，流程复杂时好管理<br>· 自带 checkpoint、人工介入<br>· 简历上写「用过 LangGraph」招聘方熟悉 | · 抽象层厚，出问题难 debug<br>· **面试官必问「为什么用 LangGraph，它帮你解决了什么」**——答不上来就完了<br>· 对一个 5 步循环属于杀鸡用牛刀<br>· 版本迭代快，容易踩坑 |
| **C Agents SDK**<br>OpenAI Agents SDK / smolagents | · 开箱即用，代码最少<br>· 能快速看到效果 | · 几乎学不到东西<br>· **面试时讲不出「你做了什么」**<br>· 绑定特定厂商生态 |
| **D 做成 Skill**<br>Claude Code / OpenClaw 的 SKILL.md | · 蹭 2026 最热的生态，天然有分发<br>· 「Agent Skill」是当下最时髦的关键词 | · ⚠️ **与项目核心目标直接冲突**：你无法控制 harness 内部的循环，<br>拿不到 token/成本统计，也无法强制结构化输出<br>· 需求 G2（产出可信数字）和 FR-9（trace 落盘）**做不了**<br>· 评测台（M6）失去意义 |

## 推荐：A 手写循环

**理由**：

1. 本项目的核心目的是展示「我知道 agent 循环里每一步在干什么」。框架会把这层遮住。
2. 我们要暴露的问题（工具报错、JSON 非法、死循环）恰恰是**手写才会遇到**的，也正是 M7 要优化改进的对象。用框架会把这些"优化空间"提前吃掉。
3. 面试时可以说：

> "我手写了 agent 循环，因为我需要完全控制 token 统计和终止条件——这决定了我能不能拿到可信的评测数据。"

**D 方案值得单独说**：它看起来最"潮"，但它和本项目的目标**根本冲突**。做 skill 就做不了评测。这个取舍本身就是很好的面试话题：

> "我考虑过做成 Claude Code skill，但那样拿不到 trace 和成本数据，评测就无从谈起。所以我选择手写循环，把可测量性放在第一位。"

# M2 · 模拟系统的形态

**决策影响**：评测要跑 100 次，形态直接决定单次耗时。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 纯 Python 内存对象** | · **快**（毫秒级）<br>· 无端口冲突、无进程管理<br>· 易测试、易打断点<br>· 可复现性天然满足（NFR-1） | · 不够"真实"<br>· 面试官可能问「你这不算真微服务吧」 |
| **B FastAPI 真 HTTP 服务** | · 真实，能演示"agent 通过 HTTP 查数据"<br>· 可以引申讲超时、重试、熔断 | · ⚠️ **慢**：每次 HTTP 几百 ms × 5 工具 × 20 场景 × 5 次 ≈ 数分钟额外等待<br>· 端口冲突、进程起停、清理都变复杂<br>· 调试要跨进程<br>· Docker 化更麻烦<br>· **面试官关心的是 agent 工程，不是你会不会写 FastAPI** |
| **C 混合**<br>数据生成用 A，另提供可选 HTTP 层 | · 两全：默认走内存（评测快），需要演示真实网络时起 HTTP<br>· 灵活 | · 多一层维护成本<br>· 两套路径容易出现行为不一致 |

## 推荐：A 为主，C 作为可选加分项

**理由**：评测要跑 100 次，**速度就是一切**。而且 HTTP 不增加任何"agent 工程"的价值。

如果时间充裕，M8 再加一个可选的 HTTP 层用于演示——但**不是必须的**。

**面试话术**：

> "模拟系统我用内存对象而不是真 HTTP 服务，因为评测要跑 100 次，HTTP 会让总耗时增加几倍，而它不改变 agent 面临的任何问题。"

# M3 · 故障怎么定义

**决策影响**：从 5 种扩到 20 种时，代码会膨胀成什么样。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 每种故障一个 Python 函数** | · 直观、可控、易调试<br>· **每种故障的"证据链"可以精心设计**（这是项目的核心手艺）<br>· 类型安全，IDE 能补全 | · 20 种 = 20 个函数，会有重复的样板代码<br>· 加故障要写代码 |
| **B 声明式 YAML** | · 加故障不用写代码<br>· 便于统一校验「不泄漏答案」<br>· 非程序员也能贡献 | · **表达力受限**：多服务级联、条件分支类的故障很难描述<br>· 调试 YAML 比调试 Python 难<br>· 要做一套解释器，等于自己造 DSL<br>· 类型安全丢失 |
| **C 原子故障 + 组合器** | · 复合故障（M8 要 3 个）天然支持<br>· 复用度高 | · 抽象成本高<br>· 5 种故障时属于过度设计<br>· 学习曲线陡 |

## 推荐：A + 抽公共 helper

**做法**：保持"一种故障一个函数"的可读性，但把重复的样板抽出来：

```python
# 每种故障只描述"事件序列"，排序/写入由 helper 负责
def inject_db_pool_exhausted(store, service, at) -> GroundTruth:
    events = build_events(...)          # 只写业务逻辑
    return emit_and_seal(events, store, service, at, ground_truth=...)  # helper 统一处理
```

**理由**：项目**最有价值的手艺**是"设计一条只有现象没有答案的证据链"——这必须用代码精心写，
YAML 表达不了这种细腻。但排序、写入这类样板应该抽掉。

**什么时候重构成 C**：如果 M8 做复合故障时发现组合逻辑重复超过三次，再抽象。

# M4 · 工具怎么切分

**注意**：这一处**已经定为 A/B 实验**（需求 §10.3），两个方案都要实现。这里列全是为了让你理解实验设计。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 按数据源切**<br>5 个：日志/指标/配置/发布/依赖 | · 语义直白，模型容易理解<br>· 实现简单，一一对应<br>· 参数模型清晰 | · 模型要自己判断"该查哪一类数据"<br>· 容易在无关数据源上瞎试，步数爆炸 |
| **B 按排障路径切**<br>3 个：`check_recent_changes` / `trace_request` / `query_metrics` | · 贴合 SRE 真实工作流<br>· 一个工具覆盖多类数据，可能减少调用次数 | · 工具内部逻辑复杂<br>· 参数表达力要求高<br>· **可能反而让模型困惑**（不知道 `check_recent_changes` 到底会查什么） |
| **C 单个通用查询工具** | · 工具数最少<br>· 不用选 | · 参数组合爆炸，模型更迷茫<br>· 无法写清晰的工具描述<br>· 基本可以确定会失败 |
| **D 在 A 的基础上加 `trace_id` 查询** | · 支持"顺着一次请求追下去"这一核心排障手法<br>· 可以在参数描述里**教 agent 排障方法** | · 参数变多<br>· 与现有 `keyword` 语义重叠 |

## 推荐：A + B 都实现（这就是实验），D 作为独立加分项

**实验结果无论正反都有价值**：

- 假设成立 → 证明你有设计判断力
- 假设不成立 → 证明你会用数据证伪自己

**这是需求里唯一的正式实验**，也是面试时最值得讲的一段：

> "我有个假设：按 SRE 排障路径切分工具比按数据源切分更有效。所以我把两个版本都实现了，
> 用同一批场景跑对比。结果是 X，这和我的预期一致/不一致，我的解释是……"

# M5 · 结构化输出怎么做

**决策影响**：`Diagnosis` 能不能稳定地被解析出来。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 手写 Pydantic 校验 + 重试** | · **完全可控**，能讲清楚每一步<br>· 无额外依赖（NFR-6）<br>· 能把"模型返回了非法 JSON"这个真实痛点暴露出来并解决<br>· 面试时能讲「我实现了校验重试」 | · 要自己覆盖各种失败模式<br>· 代码量多一些 |
| **B 用 `instructor` 库** | · 自动重试，把校验错误喂回模型<br>· 省事，几行搞定 | · 多一个依赖<br>· **面试时「我用了 instructor」不如「我实现了校验重试」有说服力**<br>· 出问题时是黑盒 |
| **C 约束解码**<br>`outlines` / provider 的 structured output | · 从**解码层**保证格式合法，最可靠<br>· 几乎不会失败 | · ⚠️ 不是所有 provider 都支持，deepseek 的支持情况需实测<br>· 失败时降级路径仍要自己写<br>· 可能限制模型表达能力 |

## 推荐：A 为核心，C 作为可选加速

**做法**：主体用手写校验 + 重试（可控、可讲），如果实测发现 provider 支持约束解码，
再作为一层"快速路径"加上，并保留手写路径作为降级。

**面试话术**：

> "结构化输出我做了两层：优先用 provider 的约束解码，不支持时降级到
> Pydantic 校验 + 把校验错误喂回模型重试。降级路径的触发率是我的一个观测指标。"

# M6 · 评测台：自建还是用现成框架

**决策影响**：**这是全项目最关键的一处选择。** 判分规则是本项目的核心差异化。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A 自建轻量评测器** | · **判分规则完全可控**——能精确实现需求 §6（服务 40% + 类别 40% + 关键词 20%）<br>· 无大依赖，安装快<br>· **面试时能讲「我怎么设计判分」**——这恰恰是绝大多数人讲不出来的<br>· 报告格式随意定制 | · 要自己写统计和报告<br>· 没有现成的可视化 |
| **B `promptfoo` / `DeepEval` / `Ragas`** | · 现成、有报告、有 UI<br>· 社区认可度高<br>· 省开发时间 | · ⚠️ **判分规则不好定制**：它们面向通用场景（准确/相关性/幻觉），<br>而我们要的是"服务名精确匹配 + 枚举精确匹配"<br>· 引入较大依赖（可能与 NFR-6 冲突）<br>· 面试时是「我配了个工具」而不是「我设计了评测」<br>· **最核心的差异化被框架吃掉了** |
| **C Langfuse / LangSmith 托管** | · trace 可视化极好<br>· 能看每一步的耗时和成本<br>· 真实公司在用 | · 要联网、要账号<br>· 数据离开本地（与"5 分钟复现"冲突）<br>· 免费额度有限<br>· 面试官要注册才能看 |

## 推荐：A 自建（必需）+ C 作为可选可视化（加分）

**理由**：

1. **判分规则是本项目的核心资产**。用通用框架就无法体现「我设计了针对这个任务的判分逻辑」。
2. 项目要展示的是「评测能力」这一项（需求 G3）。**用别人的评测框架，展示不了这个能力。**
3. 自建评测器其实不难——一个跑循环的脚本 + 一个判分函数 + 一张表，约 300 行。

**C 可以后期作为附加**：把 trace 推到本地 Langfuse，截图放进 README。
这样既有自建判分，又有专业级可视化。但**不是必需的**。

# M8 · 怎么让别人跑起来

**决策影响**：需求 G4 要求"陌生人 5 分钟内跑出结果"。

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **A README + 本地安装** | · 零成本、完全透明<br>· 面试官能看到完整代码和安装过程<br>· 没有任何前置条件（除了 Python） | · 要装 Python、装依赖（litellm 依赖较多）<br>· **5 分钟可能不够**<br>· 网络不好时会更糟（我们在国内已验证过） |
| **B Docker** | · 一条命令，环境隔离<br>· 不受本机 Python 版本影响<br>· 显得工程化 | · **面试官电脑上可能没装 Docker**<br>· 镜像大（litellm 依赖多，估计 1GB+）<br>· 国内拉镜像慢 |
| **C GitHub Codespaces / devcontainer** | · **浏览器里一键跑**，无需本地环境<br>· 开箱即用，最省事 | · 要 GitHub 账号<br>· 免费额度有限<br>· 需要能访问 GitHub（国内网络问题） |
| **D 在线 Web 演示** | · 点开链接就能看<br>· 传播性最好 | · ⚠️ 要花钱托管<br>· **API Key 要放在服务器上**（安全风险 + 可能被盗刷）<br>· **「能点开看」不如「能亲手跑」有说服力**<br>· 面试官会怀疑是不是 PPT |

## 推荐：A + B + C 三者叠加

**分层策略**：

```
第一层  README + 本地安装     ← 保底，任何人都能用
第二层  Docker               ← 有 Docker 的人一条命令
第三层  devcontainer         ← 有 GitHub 的人浏览器里跑
```

**都要做的话工作量不大**，而且每一层都在回应不同面试官的环境。

**明确不做 D**：在线演示的收益低于风险。面试时最有说服力的一句话是：

> "你 clone 下来，5 分钟就能自己跑出来，数字是真是假你自己验证。"

# 决策汇总

| 目标 | 决策 | 核心理由 |
| ---- | ---- | -------- |
| **M1** | **手写循环** | 要能逐行讲清楚，且框架会提前吃掉 M7 的优化空间 |
| **M2** | **纯 Python 内存对象**（HTTP 层可选） | 评测要跑 100 次，速度就是一切 |
| **M3** | **一故障一函数 + 抽公共 helper** | 证据链设计是核心手艺，YAML 表达不了 |
| **M4** | **A/B 都实现** | 这是唯一的正式实验，结论无论正反都有价值 |
| **M5** | **手写 Pydantic 校验 + 重试**（约束解码可选） | 可讲 > 省事 |
| **M6** | **自建评测器** | 判分规则是核心差异化，不能被框架吃掉 |
| **M8** | **README + Docker + devcontainer 三层** | 覆盖不同面试官的环境 |

## 一条贯穿所有决策的原则

> **每当"省事"和"能讲清楚"冲突时，选"能讲清楚"。**
>
> 因为本项目的目标是求职，不是交付产品。一个用五个框架拼起来的项目，
> 面试时讲不出任何东西；一个手写但每处取舍都有理由的项目，能聊一小时。

**唯一的例外**是当"省事"不影响"能讲清楚"时——比如 `typer` 做 CLI、`rich` 做输出，
这些用现成的完全没问题，因为没人会问你"为什么用 typer"。
