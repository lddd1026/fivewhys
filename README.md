# fivewhys · 五问

> Agent-driven root cause analysis. Ask why five times.

给一个「线上出错了」的场景，agent 自己查日志、查指标、查配置，连续追问「为什么」，
直到定位真正的根因。

## 这是什么

线上服务出问题的时候，值班工程师要在**日志、指标、配置、发布记录**之间来回翻，
几十分钟才能拼出根因；更麻烦的是**根因常常不在报错的那个服务上** ——
症状在上游、原因在下游，全靠人脑顺着调用链追。

这个项目把这套调查交给 agent：给它一个故障现象，它自己决定先查什么、再查什么，
连续追问「为什么」，最后交出一份**结构化的根因结论**（含证据、排除过的嫌疑、修复建议）。

关键在于**世界是造出来的**，所以标准答案在我们手里 —— 于是「诊断得对不对」
可以被自动判分。这就是它和「又一个 demo」的区别：**它有一个可测量的数字。**

## 为什么叫 fivewhys

5 Whys 是根因分析的经典方法：每得出一个原因，就继续追问它为什么会发生。

本项目把它用作 agent 的**主要停止条件**，而不是拍脑袋定一个 `max_steps = 10`。
追问到第 5 层（`FIVEWHYS_MAX_WHY_DEPTH`）、或者模型提交结论时停止。

> 诚实说明：深度是**提示词约束**，不是循环能观测到的条件 ——
> 用 tool calling 时，模型在提交前不会"暴露"自己追问到第几层。
> 实际层数可以从 `run.diagnosis.why_chain` 数出来，M6 的指标里有这一项。

## 快速开始

**不需要 API Key 就能看到结果**的部分（克隆后 1 分钟内）：

```powershell
git clone https://github.com/lddd1026/fivewhys.git
cd fivewhys
pwsh -File scripts/setup.ps1                      # 建 .venv + 装依赖（约 3 分钟）
.\.venv\Scripts\Activate.ps1

fivewhys doctor                                   # 体检：环境、模型、Key 状态
python scripts/snapshot_scenarios.py --check      # 用仓库里的指纹校验评测集没被改过
python scripts/inspect_scenario.py                # 把 5 个工具给 agent 看的东西原样打出来
python scripts/demo_m1.py --offline               # 看一个故障场景长什么样（含答案藏在哪）
```

`inspect_scenario.py` 的输出就是**这个项目的核心**：它按一次真实排障的顺序
（指标 → 日志 → 配置 → 发布 → 拓扑）调用工具，你能亲眼看到 agent 会读到什么、
哪一步查了等于没查、答案有没有从日志里泄漏出去。

**跑一次真实的诊断**（需要 API Key，会花掉约 $0.003）：

```powershell
Copy-Item .env.example .env
# 编辑 .env，填上 DEEPSEEK_API_KEY=sk-...

python scripts/demo_m1.py --runs 5 --trace        # 约 70 秒，总成本约 $0.016
```

它会按需求 §6.1 的判分规则给每次诊断打分，并打印判定：

```
┌──────┬──────┬───────────┬──────┬─────────┬───────┬──────────┐
│ 轮次 │ 得分 │ 停止原因  │ 调用 │    成本 │  耗时 │ 备注     │
├──────┼──────┼───────────┼──────┼─────────┼───────┼──────────┤
│    1 │ 100% │ submitted │    8 │ $0.0031 │ 14.0s │ 完全正确 │
│  ... │      │           │      │         │       │          │
└──────┴──────┴───────────┴──────┴─────────┴───────┴──────────┘
  通过 5/5  （判定线 80%）  总成本 $0.0156
M1 验收通过：agent 能自己查出根因。
```

**跑完看它每一步做了什么**（需求 FR-9：每次诊断都落盘完整轨迹）：

```powershell
fivewhys trace latest          # 把「模型调了什么」和「工具返回了什么」配成对显示
```

第一次失败时**先看这个** —— 能直接看出模型在哪一步走偏、读到什么才走偏的。

### 前置条件与实测环境

| 项 | 要求 / 实测 |
| --- | --- |
| Python | ≥ 3.11（实测 3.13.9） |
| 首次安装 | 约 3 分钟（实测 164 秒，官方源） |
| 跑全套测试 | 约 70 秒（实测 420 passed） |
| 平台 | 在 Windows + PowerShell 上开发与验证；纯 Python 部分不依赖平台（场景包强制 LF 换行）。`scripts/*.ps1` 是 PowerShell 脚本，Linux/macOS 用等价的 `python -m venv .venv && .venv/bin/pip install -e ".[dev]"` |
| 实测依赖版本 | `litellm==1.101.0` · `pydantic==2.13.5` · `pydantic-settings==2.15.0` · `typer==0.27.2` · `rich==15.0.0` · `python-dotenv==1.2.3`（评测数字是在这一组版本上跑出来的） |

> 依赖约束是「**下界 = 实测过的版本，上界 = 下一个主版本**」（`litellm>=1.101,<2`）。
> 原先写的 `litellm>=1.0` 是错的：我们用到的 `suppress_debug_info`、
> `_hidden_params["response_cost"]`、`acompletion(timeout=...)` 都不是 1.0 就有的 ——
> 声称支持一个从没跑过的版本，等于把问题留给第一个装它的人。
> 所以全新安装可能拿到同一主版本内更新的 `litellm`（实测 1.102.0）；
> 要完全复现上面的数字，就装回 `litellm==1.101.0`。

> ⚠️ 如果 `setup.ps1` 报 403 / 构建依赖安装失败：镜像偶尔会对 `hatchling`
> 返回 403。脚本现在会**自动换官方源重试一次**；手动重试的命令是
> `pwsh -File scripts/setup.ps1 -IndexUrl https://pypi.org/simple`

## 架构

```
              现象（question：服务名 + 粗略时间 + 表面症状）
                              │
                  ┌───────────▼────────────┐         ┌──────────────┐
                  │   agent 主循环          │◄───────►│ LLM (litellm)│
                  │   · 工具调用分发        │         └──────────────┘
                  │   · 5 Whys 追问         │
                  │   · 步数/成本熔断       │
                  └───────────┬────────────┘
                              │ 只读工具调用
                  ┌───────────▼────────────┐
                  │   5 个排障工具          │  按「一次真实排障的先后」注册
                  │   指标→日志→配置→发布→拓扑 │
                  └───────────┬────────────┘
                              │
                  ┌───────────▼────────────┐         ┌────────────────────┐
                  │   模拟系统（3 个服务）  │◄────────│  故障注入器 ×6      │
                  │   跨服务调用 + trace_id │         │  5 种故障 + 健康对照│
                  └───────────┬────────────┘         └────────────────────┘
                              │
                              ▼
        Diagnosis（9 个必填字段：根因/服务/类别/置信度/5Whys 链/证据/排除项/建议/摘要）
                              │
                              ▼
        判分（服务 40% + 类别 40% + 关键词 20%）→ 准确率 / 成本 / 延迟 / 误报率
```

**两条设计纪律**（贯穿整个项目）：

1. **日志是现象，配置是证据。** 答案藏在配置历史里（`db.pool_size: 50 -> 5`），
   日志只给症状（`connection wait time 飙升`）—— 日志里出现答案词会被自动校验拒绝。
2. **同一份事实只有一个来源。** 指标和日志来自同一批请求采样，每个服务的采样数
   必须等于「请求完成日志 + ERROR 日志」的条数，有测试守着。
3. **结论必须有据可查。** 结论里每条 evidence 的 `source` 必须指向一次**真的发生过**
   的工具调用 —— 引用了没查过的工具会被拒绝，并让它自己改。
   编造的证据读起来完全合理，而判分只看根因对不对，**所以必须由机器来查**。

## 评测结果

**M1 端到端验收**（1 个场景 × 多次，`python scripts/demo_m1.py --runs N`）

| 模型 | 根因定位准确率 | 平均工具调用次数 | 平均成本 | 平均耗时 | 通过判定 |
| ---- | -------------- | ---------------- | -------- | -------- | -------- |
| `deepseek/deepseek-chat`<sup>1</sup> | **93%**（14/15）<sup>2</sup> | 8.0 | **$0.0030** | 13.5s | ✅（判定线 3/5） |

<sup>1</sup> 请求的模型名是 `deepseek/deepseek-chat`；DeepSeek 端实际返回的
模型 id 是 `deepseek-flash`。命令与原始输出见 [docs/TASKS.md](docs/TASKS.md) 的 FIV-5。

<sup>2</sup> **样本是 4 批累加的**（5 + 5 + 3 + 2 次），其中 **1 次没到 80 分**。
一开始写的是「100%（5/5）」—— 那是真的，但只是**单个 5 次批次**；
后来又跑了几批才看到那次失败，所以这里换成了累计口径。
**一个 5 次批次不足以支撑「准确率 100%」这种说法。**
这也是 M6 要把评测集铺到 20 个场景 × 5 次的原因：样本量不够时，
准确率是估计值，不是常量 —— 而「跑 5 次至少 3 次对」本来就是个**门槛**，
不是准确率指标。

> **成本对照 NFR-2**：硬上限 $0.10/次 ✅ · 平均目标 $0.03/次 ✅（实测只有十分之一）。
> 按此推算 100 次全量评测约 $0.30，远低于 $5 的预算。
> 多轮运行有总预算闸门：`--max-total-usd`（默认 $0.50，超了就停在原地并说明原因）。

**完整改进曲线**（M6 的评测台跑起来之后往这里加行）

| baseline | — | — | — | — |

## 已知限制

写在这里而不是等人问 —— 一个项目的可信度来自它**说自己哪里不行**。

| 限制 | 影响 | 计划 |
| --- | --- | --- |
| 评测集只有 6 个场景（5 种故障 + 1 个健康对照） | 数字的统计意义有限，5/5 不能说明「准确率 100%」 | M6 铺到 20 个场景（12 单故障 + 3 复合 + 5 健康），跑 5 次取分布 |
| **没有失败重试** | 一次 429 / 网络抖动就会让该次诊断记成 `error` | M7 的对照项之一 —— 要**先测出不重试的基线**再加，否则说不清改进来自哪里 |
| **没有 trace 落盘** | 跑完只能在终端看，不能事后审计单个失败样本 | FIV-19（M5） |
| 全量评测没有总预算闸门 | 单次有 $0.10 硬上限，但 100 次连跑没有全局保险丝 | M6 的评测执行器（NFR-2 要求全量 ≤ $5） |
| 工具返回的日志文本属于**不可信输入** | 真实部署里日志可能被人为写入诱导性内容，目前没有注入防护 | 真实系统的日志确实不可信；本项目场景是我们生成的，所以先记为已知面 |
| 世界是模拟的 | 「能诊断假系统」不等于「能诊断你的生产环境」 | 这是刻意的取舍：**没有标准答案就没有评测**（见 docs/DESIGN.md 的 M2 决策） |

## 相关项目（以及本项目的区别）

做调研时发现了两个活跃的相邻项目，这里明确区分一下：

| 项目 | 它做什么 | 和 fivewhys 的区别 |
| ---- | -------- | ------------------ |
| [faultline](https://pypi.org/project/faultline/) | 给 *你自己的* agent 注入故障，测试它的韧性 | 它是**测试 agent**，不是诊断系统 |
| [whatbroke](https://pypi.org/project/whatbroke/) | 对比环境快照（依赖 / 配置 / 镜像），找出什么变了 | 它是**对比**，不做多步推理，也不看日志和指标 |
